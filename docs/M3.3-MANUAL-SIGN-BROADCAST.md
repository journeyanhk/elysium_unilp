## 1. 交易路径（与 review 的 11 项要求逐条对应）

| # | review 要求 | 实现 | 证据 |
|---|---|---|---|
| 1 | 钱包连接与当前账户确认 | 前端复用 M1 钱包连接（OKX 优先），面板显示当前账户 + 链 ID + 与 intent 用户一致性；`eth_sendTransaction` 的 `from` 必须是当前连接账户 | `frontend/src/components/SignBroadcastPanel.tsx`、`frontend/src/lib/wallet.ts` |
| 2 | 仅支持用户手动签名 | 每一次签名/广播都由用户点击触发；前端 `assertSigningAllowed()` 在**每次调用前**检查门禁/解锁记录/熔断/授权消费，任一不满足直接抛错，不弹钱包 | `frontend/src/lib/tx-sign.ts` |
| 3 | 签名前调用 pre-sign-check | 面板第 4 步为「签名前核对」，必须返回一致才允许进入第 5 步 | `routes/tx.js` `/pre-sign-check`（M3.2 第四轮已加固） |
| 4 | 校验 chainId / to / value / calldataHash | 服务端在广播前用**真实交易内容**与授权绑定逐字段比对（含发送方、selector、Gas 价格上限） | `lib/tx-wallet-tx.js` `compareTxToBinding()` |
| 5 | 校验授权状态为 authorized | 广播前必须存在 `decision='allowed'` 且 `authorization_status='consumed'` 的记录（按 intent + bindingHash + 用户定位） | `lib/tx-gate-state.js` `loadLatestAuthorization()` |
| 6 | 原子消费授权 | `POST /api/tx/consume-authorization`：先完整核对 → 条件原子 UPDATE（重复消费返回 0 行 → 拒绝）；消费后 `consumed_at` / `consumed_by` 入库 | `lib/tx-gate-state.js` `consumeAuthorization()`；`tests/tx-authorization-consumption.test.js` |
| 7 | 用户确认后请求签名 | 面板第 6 步（红色按钮）→ 钱包内人工确认；两种方式都只使用后端构建的 `to/value/data`，前端不修改任何参数 | `frontend/src/lib/tx-sign.ts` |
| 8 | 手动广播 | 方式一 `wallet-sign-raw`：钱包只签名 → 后端核对签名交易 → 后端广播（单次）；方式二 `wallet-sent`：钱包内确认并广播 → 后端按哈希事后核对 | `lib/tx-broadcast.js` |
| 9 | 等待 receipt | `POST /api/tx/receipt`：只读轮询回执（有限次），写入 `tx_broadcasts` 与审计；轮询 ≠ 重发 | `lib/tx-broadcast.js` `fetchReceipt()` |
| 10 | 失败即触发熔断 | 硬失败 → `tripKillSwitch()`：回执回滚、链上内容与授权不一致、广播结果未知（可能已进内存池） | `evaluateReceipt()` / `classifyBroadcastFailure()` |
| 11 | 写入完整审计 | 每次拒绝/广播/回执都写 `tx_audit`（含 `broadcastId`、`txHash`、拒绝码、回执摘要、偏差）；广播本身写 `tx_broadcasts` | `routes/tx.js`、`db/schema.js` `tx_broadcasts` |

## 2. 禁止事项与执行方式

| 禁止 | 执行方式 |
|---|---|
| 保存私钥 / 助记词 | 产品代码静态扫描：`lib/`、`routes/` 不得出现 `privateKeyToAccount` / `mnemonicToAccount` / `signTransaction(` / `signTypedData(`（`tests/tx-broadcast.test.js`） |
| 自动签名 | 只有前端用户点击才触发；后端不持有任何签名能力 |
| 自动重试 / 自动重发 | 广播函数为单次调用（无循环、无 `retries`、无 `nonce` 处理，静态断言）；RPC 超时按「结果未知」处理 → 熔断 + 人工确认 |
| 自动加速（speed-up）/ 替换交易 | 不存在相应方法；静态断言禁止 `speedUp/replaceTransaction/bumpFee` 等函数与手工 nonce |
| 自动放宽滑点 / 降低 minOut | 门禁参数上限不可由请求覆盖；签名交易若 Gas 价格高于上限 → 拒绝（`GAS_PRICE_OVER`） |
| 批量无人值守 | 广播必须逐笔手动触发；每分钟 1 笔、每日 3 笔上限由门禁强制 |

## 3. 广播前置检查（全部为硬条件，任一不满足即拒绝）

```
GATE_CLOSED                 交易总开关关闭
NO_UNLOCK_RECORD            缺少解锁记录
KILL_SWITCH                 熔断已触发
GATE_STATE_UNAVAILABLE      熔断状态不可读（未知 = 拒绝）
NO_AUTHORIZATION            没有授权记录
AUTHORIZATION_NOT_CONSUMED  授权未一次性消费（禁止跳过第 5 步）
CONSUMPTION_TIME_MISSING / CONSUMPTION_TIME_INVALID
CONSUMPTION_STALE           消费后超过 limits.broadcastConsumeMaxAgeSec（默认 180s）
BINDING_MISSING / BINDING_MISMATCH  绑定哈希缺失或与当前交易不一致
MODE_NOT_ALLOWED            非两种手动方式
RAW_TX_MISSING / TX_HASH_MISSING    缺少签名交易或交易哈希
```

内容核对失败码（发送前或事后）：
`CHAIN_MISMATCH` / `TO_MISMATCH` / `VALUE_MISMATCH` / `CALLDATA_MISMATCH` / `SELECTOR_MISMATCH` / `SENDER_MISMATCH` / `GAS_PRICE_OVER`。

回执核对失败码：`RECEIPT_REVERTED`（熔断）、`POST_BROADCAST_MISMATCH`（熔断）、`GAS_USD_OVER`（记录偏差，要求人工复核，不熔断）。

## 4. 失败 → 熔断对照

| 情况 | 是否熔断 | 理由 |
|---|---|---|
| 节点明确拒绝（nonce too low / insufficient funds / already known） | 否 | 交易未进入内存池，可人工复核后重来 |
| 广播请求异常 / 超时（结果未知） | **是** | 交易可能已进内存池；禁止自动重发，必须人工确认 |
| 签名交易与授权绑定不一致（发送前） | **是** | 参数被改动 |
| 回执 `status != success` | **是** | 交易回滚 |
| 链上交易内容与授权绑定不一致（事后） | **是** | 广播内容异常 |
| 同一 intent 第二次广播 | 拒绝（不熔断） | `ALREADY_BROADCAST` |
| 实际 Gas 成本超上限 | 否（记录偏差 + 要求人工复核） | 成本问题，非安全问题 |
