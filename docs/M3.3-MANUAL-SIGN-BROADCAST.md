## 0. 第一轮 review 的 P0 修复（2026-11-12）

### P0-1 签名请求显式绑定当前钱包账户

- `WalletTx` 增加 `from`；`eth_signTransaction` / `eth_sendTransaction` 参数均显式携带 `from: tx.from`（不再是 `undefined`）；
- 校验分两道（`frontend/src/lib/tx-sign.ts`）：
  - **第一道（纯函数，不接触钱包）**：门禁/解锁记录/熔断/授权已消费 + `from` 存在且合法 + `chainId === 99901` + `to` / `data` / Gas 参数齐全；
  - **第二道（读取钱包只读状态后）**：`from` 必须等于钱包当前账户（大小写不敏感）、钱包当前链必须等于交易链；
- 任一不满足 → **在请求钱包之前抛错**，不会弹出钱包；
- 后端仍保留签名恢复后的二次校验（`SENDER_MISMATCH`），不依赖前端。

测试（`frontend/src/lib/tx-sign.test.ts`，`cd frontend && bun test`，12 条）：

| 用例 | 结果 |
|---|---|
| `from` 缺失 | 拒绝，且钱包调用次数 = 0 |
| `from` 与当前账户不同 | 拒绝，且无任何签名方法调用 |
| `from` 大小写差异 | 正常通过（统一小写比较） |
| 签名恢复地址 ≠ intent 用户 | 后端拒绝（`SENDER_MISMATCH`） |
| 签名请求携带 `from`（非 undefined） | 断言请求参数中的 `from` 等于账户 |

### P0-2 Gas 参数在签名前绑定

- 新增 `lib/tx-gas.js`：
  - `gasLimit = max(ceil(eth_estimateGas × (1 + 25%)), 50000)`（余量与下限固定且文档化）；
  - `maxFeePerGas = 链上 eth_gasPrice`（必须 ≤ 5 gwei）；
  - `maxPriorityFeePerGas = min(maxFeePerGas, 1 gwei)`；
  - Gas 美元**最坏**成本 = `gasLimit × maxFeePerGas × HYPE 价格 ≤ 1 USD`；
  - 缺估算 / 缺价格 / 缺 HYPE 价格 / 超任一上限 → 计划失败（`GAS_ESTIMATE_MISSING` / `GAS_PRICE_MISSING` / `HYPE_PRICE_MISSING` / `GAS_PRICE_OVER` / `GAS_USD_OVER`）。
- `/simulate` 计算并把 Gas 计划落库（`gas_limit` / `max_fee_per_gas_wei` / `max_priority_fee_per_gas_wei` / `gas_plan_version`）并返回给前端；
- 绑定对象新增 `gasLimit` / `maxFeePerGas` / `maxPriorityFeePerGas` / `gasUsd`（进入 `bindingHash`）；
- **签名前**核对（发送前或事后，同一套检查）：
  `gasLimit ≤ 绑定值`、`maxFeePerGas ≤ 绑定值`、`maxPriorityFeePerGas ≤ 绑定值`、`优先费 ≤ maxFeePerGas`、
  `gasLimit × maxFeePerGas × HYPE 价格 ≤ 1 USD`；绑定缺 Gas 字段或取不到 HYPE 价格 → **直接拒绝**（不做事后补偿）；
- 前端签名请求显式携带 `gas` / `maxFeePerGas` / `maxPriorityFeePerGas`（来自预演锁定值），不省略、不改动。

测试（`backend/tests/tx-gas.test.js` 10 条 + `tests/tx-broadcast.test.js` 新增 5 条 + `tests/tx-presign.test.js` 新增 1 条）：

| 用例 | 结果 |
|---|---|
| `gasLimit` 被提高 | 拒绝（`GAS_LIMIT_OVER`） |
| `maxFeePerGas` 被提高（仍低于门禁 5 gwei） | 拒绝（`GAS_PRICE_OVER`，与绑定比对） |
| `maxPriorityFeePerGas` 被提高 | 拒绝（`PRIORITY_FEE_OVER`） |
| 优先费 > `maxFeePerGas` | 拒绝（`PRIORITY_FEE_ABOVE_MAX_FEE`） |
| Gas 预估缺失 / 绑定缺 Gas 字段 | 拒绝（`GAS_ESTIMATE_MISSING` / `GAS_BINDING_MISSING`） |
| Gas 美元成本超 1 USD | 拒绝（`GAS_USD_OVER`） |
| 无法获取 HYPE 价格 | 拒绝（`HYPE_PRICE_MISSING`，fail-closed） |
| 模拟记录缺 Gas 计划 | 签名前核对直接拒绝（禁止用旧记录签名） |

### 首笔模式约定（按 review）

首笔**只使用 `wallet-sign-raw`**（钱包只签名 → 后端核对 → 后端单次广播）；
`wallet-sent` 为先广播后核对、无法撤回，面板已标注「首笔不建议」。

## 0.1 第二轮 review 的 P0 / P1 修复（2026-11-12）

### P0-1 签名前重新读取服务端最新状态（不再依赖页面旧状态）

- 新增 `POST /api/tx/pre-sign-audit`（**服务端**重新读取 + 写审计快照）：
  1. 重新读取门禁状态（`enabled` / `unlockPath` / **熔断** / `stateSource` / `firstTxMode`，来自持久化）；
  2. 重新读取该 intent 的授权状态（`authorized` / `consumed` / 消费时间 / 消费时长上限）；
  3. 重新执行完整签名前核对（权威模拟记录 + 真实 calldata + 绑定逐字段比对）；
  4. 通过时返回**签名载荷**（`signing`：chainId / to / value / calldata / gasLimit / maxFeePerGas / maxPriorityFeePerGas / bindingHash），
     前端必须使用这份载荷，不得使用页面旧状态；
  5. 把整份快照写入审计（`pre-sign-verified` / `pre-sign-rejected`），字段：
     `gate`（含 version/enabled/unlockPath/killSwitchTripped/stateSource/firstTxMode）、`authorization`（含 status/bindingHash/consumedAt/consumeAgeSec）、
     `bindingHash`、`preSign`（ok/reason/changed）、`walletAccount`、`walletChainId`、`intentUser`；
     审计写入失败 → **拒绝签名**（`PRESIGN_AUDIT_FAILED`，fail-closed）。
- 新增 `GET /api/tx/authorization-state/:intentId`（只读，供前端重新读取授权状态）。
- 前端 `doSign()` 现在**每次都**：重新读取钱包账户与链 → `GET /api/tx/gate`（`cache: no-store`）→ `POST /api/tx/pre-sign-audit`
  → `evaluateFreshSignGate()` 判定（纯函数）→ 任一读取失败或判定不通过 → **直接拒绝，不弹钱包**。
- 判定覆盖：门禁关闭 / 无解锁记录 / 熔断已触发 / **熔断状态未知** / 状态不可读 / 无授权 / 未消费 /
  消费时间缺失或超时 / 服务端绑定哈希与本地不一致 / 重新核对未通过；首笔模式强制 `wallet-sign-raw`。

测试（前端 `bun test`，22 条）：页面旧状态未熔断但服务端已熔断 → 拒绝；旧状态已消费但服务端授权失效 → 拒绝；
门禁读取失败（null / 不可读）→ 拒绝；重新核对失败 → 拒绝；钱包账户切换 / 钱包链改变 → 拒绝；
另有静态断言：`doSign()` 内「新鲜状态核对 → 判定 → 钱包签名」顺序正确，且签名载荷来自服务端 `signing`。

### P0-2 Gas 参数严格等于授权绑定 + 禁止交易类型混用

- `checkGasAgainstBinding()` 由「不得超过绑定值」改为**必须严格相等**：
  `GAS_LIMIT_MISMATCH` / `MAX_FEE_MISMATCH` / `PRIORITY_FEE_MISMATCH`（**降低** Gas 参数同样拒绝 ——
  否则交易 A 的授权可被降级后的交易 B 复用）；
- **交易类型分离**：Gas 计划为 EIP-1559，legacy 交易（仅 `gasPrice`）或同时携带 `gasPrice` 的交易
  一律 `TX_TYPE_MISMATCH`（禁止「绑定 EIP-1559、实际降级 legacy」）；
- 保留绝对上限兜底（`GAS_PRICE_OVER` / `PRIORITY_FEE_ABOVE_MAX_FEE` / `GAS_USD_OVER`）与
  `HYPE_PRICE_MISSING` 的 fail-closed 行为。

测试：`tests/tx-gas.test.js`（严格相等降低/提高、legacy、混合、优先费高于 maxFee、绝对上限兜底）+
`tests/tx-broadcast.test.js`（真实签名交易的 legacy 降级、gasLimit 降低、maxFee 降低）。

### P1 首笔模式服务端禁用 wallet-sent

- `preflightBroadcast()` 增加：`gate.firstTxMode === true && mode === 'wallet-sent'` → `MODE_DISABLED_IN_FIRST_TX`
  （**服务端强制**，不只是 UI 隐藏）；
- 前端在首笔模式下禁用该选项并提示「先广播后核对，无法撤回」。

## 0.2 第三轮 review 的 P0 与观察项修复（2026-11-12）

### P0 回执阶段丢失 Gas 字段（误熔断）

**问题**：`fetchTxByHash()` 只映射了 `hash/from/to/value/input/chainId/gasPrice/maxFeePerGas/blockNumber`，
遗漏 `gas` / `maxPriorityFeePerGas` / `type`。Gas 参数自第二轮起已纳入授权绑定（**严格相等**），
于是回执核对链路（`fetchTxByHash` → `verifyReceipt` → `verifyOnChainTxAgainstBinding` → `compareTxToBinding` → `checkGasAgainstBinding`）
会得到 `gasLimit = null` / `maxPriorityFeePerGas = null` → `GAS_LIMIT_MISSING` / `PRIORITY_FEE_MISSING`
→ `POST_BROADCAST_MISMATCH` → `verification_failed` → **误触发熔断**。

**修复**：
- `fetchTxByHash()` 补齐 `type`、`gas`（→ bigint）、`maxPriorityFeePerGas`（→ bigint），并保留 `gasPrice`；
- `verifyOnChainTxAgainstBinding()` 显式传 `type` 与 `gasPriceWei`（不依赖「有 maxFeePerGas 就推断 EIP-1559」的隐式推断）；
- 回执结论带上 `contentCode`（具体失败码）与 `missingTxFields`（缺失字段清单），便于人工复核。

**回归证明**：把三个字段再次移除后跑新测试 → 复现 review 预测的失败
（`gas 必须转为 bigint` / `交易未携带 gasLimit…` / `链上交易内容与授权绑定不一致（GAS_LIMIT_MISSING）`）；恢复后 11/11 通过。

**新增集成测试** `tests/tx-receipt-integration.test.js`（11 条，**本地假节点 + 真实 JSON-RPC 十六进制载荷**，
字段由真实签名交易解析而来，不再直接构造 `GOOD_TX`）：

| 用例 | 断言 |
|---|---|
| 字段映射 | `gas` / `maxPriorityFeePerGas` 为 bigint、`type` 保留、chainId/input/from/value 正确 |
| 映射结果可核对 | `fetchTxByHash` 结果通过 `verifyOnChainTxAgainstBinding` |
| 完整链路 | RPC → `fetchTxByHash` → `verifyReceipt` → `evaluateReceipt` = `confirmed` 且 **不熔断** |
| calldata 被篡改 | `POST_BROADCAST_MISMATCH`（`CALLDATA_MISMATCH`）+ 熔断 |
| gasLimit 被篡改 | `GAS_LIMIT_MISMATCH` + 熔断 |
| 节点未返回 Gas 字段 | fail-closed 拒绝，并列出 `missingTxFields`（不默认放行） |
| legacy 交易 | `TX_TYPE_MISMATCH` + 熔断 |
| 回滚交易 | `RECEIPT_REVERTED` + 熔断 |
| 尚无回执 | `RECEIPT_PENDING` 且不熔断、不重发 |
| 发送方不符 | `SENDER_MISMATCH` + 熔断 |

### 观察项 1：钱包账户 / 链一致性改由服务端判定

签名前判定集中为纯函数 `evaluatePreSignAudit()`（`lib/tx-presign.js`），服务端显式判定
`walletAccount == intent.user_addr`（大小写不敏感）与 `walletChainId == intent.chain_id`，
失败码 `WALLET_ACCOUNT_MISMATCH` / `WALLET_ACCOUNT_MISSING` / `WALLET_CHAIN_MISMATCH` / `WALLET_CHAIN_MISSING`；
`/pre-sign-audit` 返回并审计**全部**失败原因（`snapshot.reasons`，另含 `walletAccountMatches` / `walletChainMatches`）。
后端签名恢复地址校验（`SENDER_MISMATCH`）仍作为最终兜底。

### 观察项 2：三处绑定哈希显式比对

前端 `evaluateFreshSignGate()` 现在要求 `signing.bindingHash` == `snapshot.bindingHash` == `authorization.bindingHash`
（任一不一致 → 拒绝签名），通过时把该值记入本地操作日志；后端最终校验不变。

## 0.3 第四轮 review 的修复（2026-11-12）

### 交易类型：缺失即拒绝，不做任何推断

**问题**：`normalizeTxType()` 在 `type` 缺失时仍按「是否携带 `maxFeePerGas`」推断为 EIP-1559，
与上一轮提交说明（「不再隐式推断」）及 fail-closed 要求不一致：节点若未返回 `type`，
服务端实际上并未确认交易类型，却会被当作 EIP-1559 放行。

**修复**：
- `normalizeTxType(type)` **只做归一化，不做推断**：无法识别（含缺失 / `null` / 未知类型码）→ `'unknown'`；
- `checkGasAgainstBinding()`：
  - `'unknown'` → **`TX_TYPE_MISSING`**（「节点未返回可识别类型」）；
  - 已识别但非 EIP-1559（`legacy` / `eip2930`）或同时携带 legacy `gasPrice` → **`TX_TYPE_MISMATCH`**；
  - 两个码分开，人工复核时能区分「没拿到类型」与「拿到了不允许的类型」。
- 前端签名参数（`eth_signTransaction` / `eth_sendTransaction`）**显式声明 `type: '0x2'`**，
  避免钱包静默降级为 legacy；后端仍按上面的规则独立核对。

**测试**：
- `tests/tx-gas.test.js`：`type` 缺失 / `null` / 未知类型码（`0x7f`、`0x3`）→ 全部拒绝且为 `TX_TYPE_MISSING`；
  `0x0` / `0x1` / 带 `gasPrice` → `TX_TYPE_MISMATCH`；`0x2` → 通过；`normalizeTxType` 逐一断言；
- `tests/tx-receipt-integration.test.js`：节点未返回 `type` → 回执路径 `TX_TYPE_MISSING` + 熔断 +
  `missingTxFields` 含 `type`；节点返回 `0x2` → `confirmed`；
- 前端 `bun test`：断言两种签名方式都显式带 `type: '0x2'`（且 `from` / Gas 参数同时存在）。

### 测试环境：缺表时给出可执行提示，而不是一堆失败

review 所在环境缺少 `tx_gate_attempts` / `tx_gate_buckets` / `tx_gate_reservations`，
导致 22 条失败（正好是需要数据库的三个文件）。新增 `tests/helpers/db-required.js`：
- 运行前检查所需 M3 表是否齐全；
- 缺表 → 该文件的测试**逐条跳过**并提示「先启动一次后端以自动同步 schema」；
- 后端重启窗口导致的连接错误会先重试 3 次（避免误判为缺表）。

**测试运行前置条件**：后端处于运行且稳定状态（文件变更会触发后端重启，重启窗口内跑数据库相关测试可能不稳定）。
在稳定环境下连续 3 次全量运行：**252/252 通过**。

## 0.4 第五轮 review：测试门禁问题的修复（2026-11-12）

### 核心交易链路：复核通过

review 明确「签名、广播、Gas、交易类型、回执核对这条核心链路没有再发现新的 P0 绕过口」。
本轮不涉及交易逻辑改动。

### 问题 1：跳过机制没有真正生效（根因是包装器自身失效）

**现象**：缺表环境运行全量测试 → 22 条失败、0 条跳过（review 实测）。

**根因（两层）**：
1. 包装器写成 `nodeTest.test(name, options, runner)`；当调用方只传 `(name, fn)` 时 `options` 为 `undefined`，
   node 的测试运行器**不会执行 `runner`** —— 用例变成「空用例」直接通过，跳过逻辑形同虚设；
2. 三个数据库测试文件里的 `test.before()` 钩子会先做数据库清理，钩子抛错会让**整个文件**的用例判失败，
   逐条跳过根本轮不到执行。

**修复**：
- 包装器改为：`options` 为函数或空时用 `nodeTest.test(name, runner)`，否则用三参数形式；
- 包装器同时接管 `before / after / beforeEach / afterEach`：数据库不可用时钩子**不执行**（避免钩子把整文件判失败）；
- 表存在性检查改用 `to_regclass()`（与业务查询**同一套 search_path 解析**），避免「检查认为存在、业务查询却找不到」；
- 跳过原因包含：缺失表名、`current_database()`、`current_schema()`、`search_path`、当前用户、两条修复办法。

## 0.5 review 第五轮追加：清理钩子保护的修复（2026-11-12）

### 问题：缺表环境下 `after` 清理钩子仍执行并失败（2 个失败）

**根因**：包装器里的钩子保护写成了 `(name, fn) => register(name, wrapped)`，而 **node 的钩子签名是 `before(fn[, options])`（没有名字参数）**。
于是当调用方写 `test.after(async () => {...})` 时：`name` = 用户的原始函数、`fn` = `undefined` → `register(用户函数, wrapped)`
→ node 只认第一个参数 → **注册的是用户的原始函数，我的保护函数被忽略**。
结论：所谓「钩子保护」从未生效，缺表环境下清理钩子照旧执行 `DELETE`，于是 2 个文件各报 1 个失败。

**修复**：
- `guardHook` 改为按 `(fn, options)` 处理（非函数时原样透传）；
- 三个数据库测试文件的 `before` / `after` 钩子**再加一层文件级保护**：钩子内显式调用 `test.isDbReady()`，
  数据库不可用（缺表 / 连不上）时直接返回，不执行任何清理 SQL；
- 包装器新增 `isDbReady()` 供测试文件使用（`dbStatus()` 仍然可用）。

**新增实测（review 明确要求的「最小复现」）** `tests/db-required-helper.test.js`（子进程实测，共 7 条）：

| 用例 | 断言 |
|---|---|
| 缺表环境：四种钩子都不得执行 | 标记文件不存在（`before`/`beforeEach`/`afterEach`/`after` 全部不执行）+ `fail=0` + `skipped=1` |
| 表齐全环境：钩子必须真的执行 | 标记文件包含 `before;after;body;`（证明保护不是「一刀切不执行」） |
| 文件级保护 | 钩子内先查 `isDbReady()`，缺表时访问不存在的表也不失败 |
| 对照组（无保护） | 直接使用 `node:test` 的钩子访问不存在的表 → **必须失败**（证明该类问题可被检出，测试非空转） |
| 用例体执行 / 跳过 | 缺表必须 `skipped`；表齐全时用例体抛错必须体现为 `fail=1` |

**反向验证**：把钩子包装改回错误签名 → 「缺表环境四种钩子都不得执行」立即失败；恢复后 7/7 通过。

### 同时修正：测试不得对**写操作**做自动重试

上一轮为避免数据库接口限流（429）在测试侧加了退避重试，并注入到了额度**占用/释放**路径上 ——
这与本项目自己的规则冲突（写操作不得自动重试）。现已移除写路径上的全部重试注入，
只保留**只读**调用（`loadBuckets` / `loadReservation` / `loadLatestAuthorization`）的限流重试；
限流本身由运行器节奏控制（见下）。

## 0.6 review 第六轮：测试门禁防「假绿」（2026-11-12）

review 第六轮结论：钩子签名修复方向正确、缺表路径实际通过（`fail=0`）、交易安全专项无新 P0；
但发现**测试门禁仍可能假绿**，以及**子进程自检在干净检出中不可复现**。本轮三项修复：

### P0：完整环境的判据必须同时包含 `skipped=0`

**问题**：`scripts/run-backend-tests.sh` 只看 `# fail`，不看 `# skipped`。
若数据库缺表 / 连不上 / 限流导致 helper 判定数据库不可用，用例会被**跳过**，而脚本仍以 `fail=0` 计为 clean run
→ 输出「3 次全绿」的假象。

**修复**：脚本现在解析 `fail` 与 `skipped`，四分支明确区分：

| 情况 | 处理 |
|---|---|
| `fail=0` 且 `skipped=0` | 计为一次 clean run（完整环境通过） |
| `fail=0` 但 `skipped>0` | **判为「不是完整环境」，不计为通过、不重跑**（并提示先 `bun run db:ensure`） |
| `fail>0` 且输出明确含 `RATE_LIMITED` | 环境限流 → 等待 120 秒重跑该次（最多 3 次尝试） |
| 其余（含缺表、连接错误、断言失败） | 真实失败 → 立即报告，绝不归类为限流 |

最终输出也改为明确口径：`✓ 完整环境：N 次连续运行均为 fail=0、skipped=0`。

### P1：子进程探针的独立可复现性

**问题**：探针文件写在系统临时目录（`/tmp/dbwrap-*`），在部分环境中无法解析 `@surf-ai/sdk/db`，
导致自检在进入包装器逻辑前就退出 —— 那样「7/7 通过」就无法独立复现，也失去了防退化意义。

**修复（三重保险）**：
1. 探针目录改为项目内 `backend/tests/.tmp/`（祖先目录含 `backend/`，Node 依赖解析自然生效）；
2. 子进程显式设置 `NODE_PATH` 指向 `backend/node_modules`（含上层工作区 `node_modules`）作为兜底；
3. 子进程**先做 SDK 解析自检**并把解析到的路径写入文件；父测试断言解析成功、指向真实文件、探针目录在项目内
   —— 依赖解析失败会被明确报告为「解析失败」，而不会被误读成「包装器逻辑失败」。

**新增实测**：
- 「子进程探针必须能独立解析 SDK 依赖（不依赖运行目录、不在系统 /tmp）」；
- 「从项目外的目录运行本文件也必须全绿（独立检出可复现）」——用项目根之外的工作目录启动同一测试文件并断言 `fail=0`。

> 诚实说明：在本沙箱环境中，把探针放回系统 `/tmp` 也**能**解析到 SDK（Node 按「引入方所在目录」逐级查找），
> 因此本环境**无法复现** review 环境中的 `Cannot find module '@surf-ai/sdk/db'`。
> 上述三重保险 + 自检使该问题在**任何**环境下都变成「明确可诊断」，而不是静默失效。

### P1：文档不再写死测试总数

验收口径统一为：完整环境 `fail=0` **且 `skipped=0`**；缺表环境 `fail=0` 且数据库用例全部 `skipped`。
仓库内已无把 `259` / `263` 当作长期安全标准的表述（数量随迭代变化）。

## 4. 失败 → 熔断对照

| 情况 | 是否熔断 | 理由 |
|---|---|---|
| 节点明确拒绝（nonce too low / insufficient funds / already known） | 否 | 交易未进入内存池，可人工复核后重来 |
| 广播请求异常 / 超时（结果未知） | **是** | 交易可能已进内存池；禁止自动重发，必须人工确认 |
| 签名交易与授权绑定不一致（发送前） | **是** | 参数被改动 |
| 回执 `status != success` | **是** | 交易回滚 |
| 链上交易内容与授权绑定不一致（事后） | **是** | 广播内容异常 |
| 同一 intent 第二次广播 | 拒绝（不熔断） | `ALREADY_BROADCAST` |
| 实际 Gas 成本超上限 | 否（记录偏差 + 要求人工复核） | 成本问题，非安全问题 |

- [ ] 缺表环境下 `before` / `beforeEach` / `afterEach` / `after` 四种钩子是否**都不执行**
- [ ] 缺表环境全量测试是否为 `fail=0`（清理钩子不得报错）
- [ ] 表齐全环境下钩子是否**确实执行**（防止保护变成「一刀切」）
- [ ] 钩子内是否有文件级 `isDbReady()` 保护（不依赖外层包装）
- [ ] 写操作（额度占用/释放）路径上是否**没有任何**自动重试
- [ ] 运行器是否在限流时等待重跑，并明确区分「环境限流」与「代码失败」
- [ ] 运行器是否**同时要求 `fail=0` 与 `skipped=0`**（`fail=0` 但 `skipped>0` 必须判为「不是完整环境」而非通过）
- [ ] 运行器是否只在「有失败且输出明确含 `RATE_LIMITED`」时才重跑（缺表/连接错误/断言失败一律按真实失败处理）
- [ ] 子进程探针是否放在项目内（`backend/tests/.tmp/`）、是否设置 `NODE_PATH` 兜底、是否先做 SDK 解析自检
- [ ] 文档中是否已无写死的测试总数（验收只按 `fail` / `skipped`）

**第五轮修复验收点**

- [ ] 缺表环境下全量测试是否为 `fail=0` 且数据库相关用例 `skipped`（而不是失败）
- [ ] 跳过原因是否列出：缺失表名 / 当前数据库 / 当前 schema / search_path / 修复命令
- [ ] 包装器防退化测试是否通过（子进程实测：缺表跳过、表齐全时必须真正执行用例体）
- [ ] 完整环境连跑 3 次是否均 `fail=0`（建议用 `bun run test:full`，避开数据库接口限流）
- [ ] `bun run db:ensure` 是否幂等（重复执行不报错、不重复建表）
- [ ] `tests/db-schema-parity.test.js` 是否守护建表脚本与 schema 一致

**第四轮修复验收点**

- [ ] `type` 缺失 / `null` / 未知类型码是否**拒绝**（`TX_TYPE_MISSING`），而不是推断为 EIP-1559
- [ ] `0x0` / `0x1` / 带 legacy `gasPrice` 是否 `TX_TYPE_MISMATCH`
- [ ] 回执路径在节点未返回 `type` 时是否 fail-closed 并熔断（`missingTxFields` 含 `type`）
- [ ] 前端两种签名方式是否都显式声明 `type: '0x2'`
- [ ] 缺表环境是否显示为「跳过 + 提示」而不是失败

**第三轮 P0 与观察项修复验收点**

- [ ] `fetchTxByHash()` 是否返回 `type` / `gas` / `maxPriorityFeePerGas`（并转 bigint）
- [ ] 回执核对链路是否用**真实 RPC 载荷**测过（不是直接构造 `GOOD_TX`）
- [ ] 成功且正确的交易在回执阶段是否为 `confirmed` 且**不熔断**
- [ ] 内容不符 / Gas 不符 / legacy / 回滚 / 发送方不符是否仍然熔断
- [ ] 节点未返回 Gas 字段时是否 fail-closed 拒绝并列出缺失字段（不默认放行）
- [ ] 钱包账户与链一致性是否由**服务端**判定并审计
- [ ] 签名载荷 / 快照 / 授权三处绑定哈希是否一致

**第二轮 P0 / P1 修复验收点**

- [ ] 每次点击签名前是否重新读取门禁 / 熔断 / 授权状态与钱包账户（不依赖页面旧状态）
- [ ] 重新读取失败（网络错误、接口非 200、状态不可读）是否 fail-closed 拒绝且不弹钱包
- [ ] 签名载荷是否来自服务端「签名那一刻」返回的 `signing`（而不是页面保存的 intent / gasPlan）
- [ ] 门禁快照是否写入审计（gate / authorization / bindingHash / preSign / walletAccount / walletChainId）
- [ ] 审计写入失败是否导致拒绝签名
- [ ] Gas 参数是否**严格等于**绑定值（降低也拒绝），错误码是否区分三类
- [ ] legacy 交易（或同时带 gasPrice 的交易）是否被 `TX_TYPE_MISMATCH` 拒绝
- [ ] 首笔模式下 `wallet-sent` 是否被**服务端**强制禁用

**第一轮 P0 修复验收点**

- [ ] `eth_signTransaction` / `eth_sendTransaction` 是否显式携带 `from`，且等于钱包当前账户
- [ ] `from` 缺失 / 不一致 / 链不符时是否**在请求钱包之前**拒绝（前端测试断言钱包调用次数）
- [ ] 后端是否仍保留签名恢复后的发送方二次校验
- [ ] Gas 计划是否在 simulate 阶段固定并落库（gasLimit / maxFeePerGas / maxPriorityFeePerGas）
- [ ] 授权绑定是否包含 Gas 字段（进入 bindingHash）
- [ ] 签名前核对是否拒绝「gasLimit / maxFeePerGas / maxPriorityFeePerGas 超过绑定值」
- [ ] Gas 美元上限是否前置到签名前（含无法获取 HYPE 价格时 fail-closed）
- [ ] 模拟记录缺 Gas 计划时是否拒绝签名

**架构与状态**

- [ ] 广播前置检查的每条拒绝码是否都对应真实实现，且**全部在发送之前**执行（`tests/tx-broadcast.test.js` 静态顺序断言）
- [ ] 广播是否**只有单次调用**（无重试 / 无替换 / 无加速 / 无手工 nonce）
- [ ] 签名交易核对是否覆盖 chainId / to / value / calldataHash / selector / 发送方 / Gas 价格上限
- [ ] 钱包自行广播（`wallet-sent`）的事后核对是否能在内容不符时熔断
- [ ] 回执核对是否覆盖 status / 内容一致性 / Gas 偏差，失败是否正确熔断
- [ ] 授权是否必须「已一次性消费」才能广播，且消费超时会被拒绝
- [ ] 同一 intent 是否禁止第二笔广播
- [ ] 审计是否覆盖拒绝、广播、回执三类事件，且失败不改变拒绝结果
- [ ] 前端是否在每次签名前重新检查门禁/熔断/消费状态（不依赖 UI 状态）
- [ ] 产品代码是否仍无任何签名能力（静态扫描）
- [ ] 全部开关是否保持关闭：`TX_GATE.enabled=false`、`unlockRecord.path=null`、所有 `writeEnabled=false`
